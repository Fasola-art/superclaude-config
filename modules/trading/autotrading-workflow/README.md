## 시스템 개요

이 시스템은 사람이 24시간 시장을 감시하는 대신, 여러 대의 컴퓨터가 역할을 나눠 자동으로 매매합니다.

**핵심 아이디어**:
- 뉴스가 나오면 LLM이 "이건 호재인가 악재인가" 판단하고,
- 강화학습 에이전트가 "지금 사야 하나 팔아야 하나" 결정하고,
- 리스크 관리가 "이 정도면 안전한가" 검증한 뒤,
- 브로커 API로 실제 주문을 넣습니다.

**3계층 의사결정**:
```
Layer 1: LLM 분석       →  "지금 상황이 어떤가?" (컨피던스 스코어 0~1)
Layer 2: RL Agent        →  "그래서 뭘 할까?" (BUY / SELL / HOLD)
Layer 3: Rule-Based 폴백 →  "RL이 못 하면 내가 한다" (EMA/RSI/볼린저)
```

**검증 절차** (실제 돈을 넣기 전에 반드시 거치는 3단계):

| 순서 | 단계 | 최소 기간 | 통과 기준 |
|------|------|----------|----------|
| 1 | 백테스팅 (과거 데이터) | 2주 | Sharpe ≥ 1.5, MDD ≤ 15% |
| 2 | 페이퍼 트레이딩 (가상 돈) | 30일 | 월 수익 양수, 시스템 안정 |
| 3 | 소액 실거래 (진짜 돈) | 점진적 | $500 → $2K → $5K → $10K+ |

## 1. 의사결정 — 뭘 살까?

### LLM 4-Agent 파이프라인

시장에서 새로운 정보가 들어오면 4개의 전문 에이전트가 동시에 분석을 시작합니다.
각 에이전트는 자기 전문 분야만 분석하고, 마지막에 SignalAgent가 종합합니다.

```
뉴스 도착 ──→ NewsAgent ──┐
지표 발표 ──→ MacroAgent ─┤──→ SignalAgent ──→ 최종 컨피던스 (0.0 ~ 1.0)
젯슨 YOLO ──→ TechAgent ──┤
스케줄    ──→ (정기 분석) ──┘
```

| 에이전트 | 모델 | 분석하는 것 | 가중치 | 설명 |
|---------|------|-----------|--------|------|
| NewsAgent | Qwen 3B/7B | 뉴스 감성, 영향 종목 | 25% | "이 뉴스는 AAPL에 호재인가?" |
| MacroAgent | Qwen 3B/7B | FRED 지표, FedWatch, COT | 25% | "금리가 오를까? 경기가 좋아질까?" |
| TechAgent | Qwen 3B + YOLO | EMA 배열, 차트 패턴, 거래량 | 30% | "차트가 매수 신호를 보이는가?" |
| SignalAgent | Qwen 7B | 위 3개 통합 검증 | 20% | "종합적으로 신뢰할 만한가?" |

**컨피던스 합산 공식**:
```python
final_confidence = (
    news_conf * 0.25 +     # 뉴스 분석 결과
    macro_conf * 0.25 +    # 매크로 분석 결과
    tech_conf * 0.30 +     # 기술적 분석 결과 (가장 높은 비중)
    signal_conf * 0.20     # 통합 검증 결과
)
# 0.7 이상이면 시그널 발행
```

### 에스컬레이션 (모델 크기 점진적 확대)

작은 모델로 빠르게 판단하되, 애매하면 더 큰 모델에 물어봅니다.

```
Mac Studio (Qwen 3B/7B) — 1차 분석 (대부분 여기서 해결)
    │
    ├── 컨피던스 ≥ 0.6 → 시그널 발행 (빠르고 저렴)
    │
    ├── 컨피던스 < 0.6 → 4090 노트북 (Qwen 14B~72B) — 2차 분석
    │   ├── 컨피던스 ≥ 0.6 → 시그널 발행
    │   └── 컨피던스 < 0.6 → Claude API — 최종 판단 (가장 정확하지만 비용 발생)
    │
    └── 복잡한 다중 요소 분석 → Claude API 직접 호출
```

### Rule-Based 폴백 (안전망)

RL Agent가 아직 배포 전이거나, 신뢰도가 낮을 때 작동하는 전통적인 규칙입니다.
시스템 장애 시에도 자동으로 이 모드로 전환됩니다.

| 조건 | 시그널 | 신뢰도 |
|------|--------|--------|
| EMA 8 > 16 > 32 (정배열) + RSI < 70 | BUY | 0.6 |
| EMA 8 < 16 < 32 (역배열) + RSI > 30 | SELL | 0.6 |
| 볼린저 하단 터치 + RSI < 30 | BUY | 0.5 |
| 볼린저 상단 터치 + RSI > 70 | SELL | 0.5 |
| MACD 골든크로스 + 거래량 2배 이상 | BUY | 0.7 |

### MQTT 토픽 (내부 통신)

각 에이전트는 MQTT 메시지 브로커를 통해 분석 결과를 공유합니다.

| 토픽 | 발행자 | 내용 |
|------|--------|------|
| `analysis/{symbol}/news` | NewsAgent | 뉴스 분석 결과 |
| `analysis/{symbol}/macro` | MacroAgent | 매크로 분석 결과 |
| `analysis/{symbol}/tech` | TechAgent | 기술적 분석 결과 |
| `signal/{symbol}/decision` | SignalAgent/RL | 최종 매매 시그널 |

## 2. 강화학습 에이전트

LLM이 "상황 분석"을 해주면, RL Agent가 "그래서 뭘 할지" 최종 결정합니다.
게임을 반복 플레이해서 실력을 키우듯, 과거 시장 데이터로 매매를 반복 학습합니다.

### 알고리즘

| 알고리즘 | 용도 | 특성 |
|---------|------|------|
| PPO (기본) | 안정적 학습, 초기 배포에 적합 | on-policy, 안전하게 학습 |
| SAC (고급) | 연속 행동 공간 최적화 | off-policy, 데이터 효율이 좋음 |

### State Space (RL이 보는 것, ~30개 변수)

RL Agent는 매 순간 약 30개의 숫자를 입력받아 판단합니다.

| 카테고리 | 어떤 정보인지 | 변수 수 |
|---------|-------------|--------|
| 가격 | 수익률, 변동성, ATR (평균 진폭) | 5개 |
| 기술지표 | RSI, MACD, 볼린저밴드 위치, EMA 배열 상태 | 8개 |
| 거래량 | 거래량 비율, OBV (누적 거래량), CVD | 4개 |
| LLM 컨피던스 | 뉴스/매크로/기술/시그널 각각의 점수 | 4개 |
| 포지션 상태 | 현재 보유 여부, 손익, 보유 시간 | 3개 |
| 매크로 | VIX (공포지수), DXY (달러), 금리 스프레드 | 3개 |
| 시장 레짐 | 변동성 상태, 추세 강도 | 3개 |

정규화: 가격은 z-score, 지표는 0~1, 매크로는 min-max 스케일링.

### Action Space (RL이 하는 것)

| 행동 | 값 | 설명 |
|------|------|------|
| BUY | 0 | 매수 (사이즈 0.1~1.0 범위) |
| SELL | 1 | 매도 (사이즈 0.1~1.0 범위) |
| HOLD | 2 | 아무것도 안 함 |

포지션 사이즈는 `base_size × confidence`로 계산됩니다.
자신이 높을수록 크게, 낮을수록 작게 진입합니다.

### Reward Function (RL이 배우는 기준)

"좋은 매매란 무엇인가"를 정의하는 보상 함수입니다.

| 구성 요소 | 계산 방법 | 왜 이렇게 하는지 |
|----------|----------|----------------|
| 기본 보상 | PnL% × 100 | 수익을 내면 보상, 손실이면 벌점 |
| Sharpe 보너스 | +0.5 (Sharpe > 1.5일 때) | 안정적으로 수익 내는 것을 장려 |
| MDD 페널티 | -drawdown × 10 (DD > 10%) | 큰 손실을 내면 강하게 처벌 |
| 과거래 페널티 | -0.3 × (거래수 - 20) | 하루 20회 초과하면 벌점 (불필요한 매매 억제) |
| 거래 비용 | -0.1 (매매할 때마다) | 수수료를 반영해 꼭 필요할 때만 거래 유도 |

### 학습 스케줄

| 항목 | 설정 |
|------|------|
| 학습 디바이스 | 4090 노트북 (야간 00:00~06:00에만 가동) |
| 추론 디바이스 | Mac Studio (24시간 가동) |
| 학습 주기 | 주 1회 (주말 야간) |
| 에피소드 | 학습 1회당 1000+ 에피소드 |
| 학습률 | 3e-4 (PPO, SAC 동일) |
| 배치 크기 | 256 steps |
| 학습 데이터 | 최근 6개월 시장 데이터 |

### 모델 관리

학습된 모델은 `~/.claude/modules/trading/models/rl/`에 저장됩니다.
파일명 형식: `PPO_BTCUSDT_20260207.zip`

- 최근 5개 체크포인트를 보존합니다
- 성능이 떨어지면 이전 모델로 자동 롤백합니다

### BaseStrategy 인터페이스

모든 전략은 `BaseStrategy`를 상속하며, RL도 마찬가지입니다.

```python
class RLStrategy(BaseStrategy):
    def __init__(self, algo: str = 'PPO', model_path: str = None):
        super().__init__(name=f'RL-{algo}')
        self.algo = algo
        self.model = self._load_model(model_path)

    def generate_signal(self, data: dict) -> TradeSignal:
        state = self.build_state(data)                              # 30개 변수 구성
        action, _states = self.model.predict(state, deterministic=True)  # RL 추론
        confidence = self._get_action_probability(state, action)    # 확신도 추출
        return TradeSignal(
            timestamp=data['timestamp'],
            symbol=data['symbol'],
            signal_type=self._map_action(action),   # 0→BUY, 1→SELL, 2→HOLD
            side=self._map_side(action),
            price=data['price'],
            confidence=float(confidence),
            reason=f'RL-{self.algo}: action={action}, conf={confidence:.2f}'
        )
```

## 3. 리스크 관리 — 얼마나 살까?

매매 결정이 내려져도 곧바로 실행하지 않습니다.
3단계 리스크 관리를 통과해야 실제 주문이 나갑니다.

### 서킷브레이커 (3단계 비상 브레이크)

주식시장의 서킷브레이커처럼, 손실이 커지면 자동으로 거래를 제한합니다.

| Level | 발동 조건 | 시스템이 하는 일 | 복구 방법 |
|-------|----------|----------------|----------|
| WARNING | 일일 손실 -3% | 포지션 사이즈를 50%로 줄임 | 다음 날 자동 해제 |
| CRITICAL | 일일 손실 -5% | 새로운 진입 완전 중단 (기존 유지) | 사용자가 수동으로 승인 |
| EMERGENCY | 총 자산 -10% | 모든 포지션 즉시 청산, 시스템 정지 | 사용자가 수동으로 재개 |

### Per-Trade 리스크 (거래 하나하나마다)

**원칙**: 한 번의 거래로 총 자본의 2% 이상 잃지 않도록 합니다.

**ATR 기반 손절 설정**:
```python
# 예시: 자본 $10,000, ATR = $5인 종목
risk_per_trade = 10000 * 0.02          # = $200 (한 거래 최대 손실)
stop_distance = 5.0 * 2.0              # = $10 (ATR의 2배 거리에 손절)
position_size = 200 / 10               # = 20주 (이 정도 사면 손절 시 $200 손실)
```

**주문별 설정**:

| 주문 유형 | 기준 | 의미 |
|----------|------|------|
| Stop-Loss (손절) | ATR × 2.0 | "여기까지 떨어지면 내 분석이 틀린 것" |
| Take-Profit (익절) | ATR × 3.0 | 손절 대비 1.5배 수익 (R:R = 1:1.5) |
| Trailing Stop | ATR × 1.5 | 수익이 나면 손절선을 따라 올림 |

### Daily 리스크 (하루 단위)

| 항목 | 한도 | 왜? |
|------|------|-----|
| 최대 일일 손실 | -5% | 하루에 너무 많이 잃지 않도록 |
| 최대 동시 포지션 | 5개 | 너무 많은 종목에 분산되지 않도록 |
| 최대 동일 섹터 | 2개 | 같은 업종에 몰빵하지 않도록 |
| 최대 일일 거래 | 20회 | 의미없는 과거래 방지 |

**상관관계 리스크**:
```python
# 같은 섹터에 30% 이상 투자하면 새 진입 거부
sector_exposure = sum(position.weight for p in positions if p.sector == sector)
if sector_exposure > 0.30:
    reject_new_entry(symbol)

# 상관관계 0.8 이상인 종목 쌍은 합산 비중 20% 제한
correlation = calculate_correlation(symbol_a, symbol_b, window=60)
if correlation > 0.8:
    reduce_combined_size(max_weight=0.20)
```

### Total 리스크 (전체 포트폴리오)

| 항목 | 한도 | 모니터링 주기 |
|------|------|------------|
| 최대 MDD (최대 낙폭) | -15% | 실시간 |
| 최대 투자 비율 | 80% (항상 20%는 현금) | 일일 점검 |
| VaR (95% 신뢰구간) | -3% | 일일 계산 |

### ATR 기반 동적 포지션 사이징

변동성이 큰 종목은 작게, 작은 종목은 크게 진입합니다.

```python
def calculate_position_size(
    capital: float,        # 총 자본
    price: float,          # 현재 가격
    atr: float,            # 14일 ATR
    risk_pct: float = 0.02,      # 거래당 리스크 (2%)
    atr_multiplier: float = 2.0  # 손절 거리 배수
) -> float:
    """리스크 기반 포지션 크기 계산"""
    risk_amount = capital * risk_pct          # $200 (자본의 2%)
    stop_distance = atr * atr_multiplier      # 손절까지의 가격 거리
    shares = risk_amount / stop_distance      # 이 주수만큼 사면 손절 시 $200 손실
    max_position = capital * 0.20             # 단일 포지션 최대 20%
    return min(shares, max_position / price)  # 둘 중 작은 값
```

## 4. 주문 실행 — 어떻게 살까?

리스크 검증을 통과하면, 사무용 데스크탑(24시간 가동)이 실제 브로커에 주문을 넣습니다.

### 브로커 연동

| 브로커 | 자산군 | API 라이브러리 | 실행 디바이스 |
|--------|--------|--------------|-------------|
| MT5 (키움) | 한국 주식/선물 | MetaTrader5 Python | 사무용 데스크탑 |
| Binance | 크립토 (비트코인 등) | python-binance | 사무용 데스크탑 |
| IBKR | 해외 주식/선물 | ib_insync | 사무용 데스크탑 |
| 토스증권 | 한국 주식 (간편) | REST API | 모바일 (수동) |

### 주문 유형

| 유형 | 용도 | 파라미터 |
|------|------|---------|
| Market | 지금 당장 사야 할 때 | symbol, side, qty |
| Limit | 특정 가격에 사고 싶을 때 | + price |
| Stop-Loss | 손절가에 도달하면 자동 매도 | trigger_price |
| Take-Profit | 목표가에 도달하면 자동 매도 | target_price |
| Trailing Stop | 수익을 보호하면서 추세 추종 | trail_distance (ATR 기반) |
| OCO | 손절과 익절을 동시에 걸어둠 | stop_price + take_price |

### 주문 실행 파이프라인

시그널이 MQTT로 도착하면 아래 순서로 처리됩니다.

```
시그널 수신 (MQTT: signal/{symbol}/decision)
    │
    ├── 1. 리스크 검증
    │   ├── 서킷브레이커 상태 확인 (WARNING/CRITICAL이면 제한)
    │   ├── 일일 거래 한도 확인 (20회 초과하면 거부)
    │   └── 포지션 사이즈 계산 (ATR 기반)
    │
    ├── 2. 주문 생성
    │   ├── 자산군에 맞는 브로커 API 선택
    │   ├── 슬리피지 보정 (±0.1%)
    │   └── 수수료 계산
    │
    ├── 3. 주문 전송
    │   ├── 체결 대기 (최대 30초)
    │   ├── 부분 체결 시 나머지 처리
    │   └── 실패 시 최대 3회 재시도
    │
    └── 4. 주문 추적
        ├── Redis Pub/Sub로 상태 실시간 발행
        ├── 체결 확인 → PostgreSQL DB에 기록
        └── 손절/익절 연동 주문 자동 설정
```

### 슬리피지 & 수수료

실제 거래에서 발생하는 비용입니다. 백테스팅에도 동일하게 반영됩니다.

| 자산군 | 예상 슬리피지 | 수수료 | 스프레드 |
|--------|-------------|--------|---------|
| 한국주식 | 0.05% | 0.015% (키움) | - |
| 미국주식 | 0.03% | $0 (IBKR Lite) | - |
| 크립토 | 0.10% | 0.10% (Binance) | 0.01% |
| 선물 | 1 tick | $2/계약 | 1 tick |

### 주문 상태 관리

주문은 아래 상태를 순서대로 거칩니다.

```
PENDING → SUBMITTED → FILLED (정상 완료)
                    → PARTIALLY_FILLED → FILLED (부분 체결 후 완료)
                    → CANCELLED (취소됨)
                    → REJECTED (거부됨)
                    → EXPIRED (만료됨)
```

주문 상태는 Redis Pub/Sub(`order/{order_id}/status`)로 실시간 발행되어,
모니터링 대시보드에서 바로 확인할 수 있습니다.

## 5. 백테스팅 — 전략 검증

실제 돈을 넣기 전에, 과거 3년간의 데이터로 전략이 제대로 작동하는지 검증합니다.

### 승인 기준 (이걸 통과해야 다음 단계로)

| 지표 | 최소 기준 | 우수 기준 | 측정 기간 |
|------|----------|----------|----------|
| Sharpe Ratio | ≥ 1.5 | ≥ 2.0 | 1년 |
| Max Drawdown (최대 낙폭) | ≤ 15% | ≤ 10% | 전체 |
| Win Rate (승률) | ≥ 55% | ≥ 60% | 전체 |
| Profit Factor | ≥ 1.5 | ≥ 2.0 | 전체 |
| 거래 횟수 | ≥ 100회 | ≥ 200회 | 전체 |

### Walk-Forward Validation

단순히 과거 전체로 테스트하면 과적합 위험이 있습니다.
그래서 데이터를 시간순으로 나눠, "학습 → 검증 → 테스트"를 4번 반복합니다.

```
전체 데이터 (3년)
├── Window 1: [학습 12개월] [검증 3개월] [테스트 3개월]
├── Window 2:    [학습 12개월] [검증 3개월] [테스트 3개월]
├── Window 3:       [학습 12개월] [검증 3개월] [테스트 3개월]
└── Window 4:          [학습 12개월] [검증 3개월] [테스트 3개월]

4개 테스트 결과를 합산해서 최종 성과를 평가합니다.
```

| 구간 | 비율 | 용도 |
|------|------|------|
| 학습 (Train) | 60% | 전략 파라미터 최적화 |
| 검증 (Validation) | 20% | 하이퍼파라미터 선택 |
| 테스트 (Test) | 20% | 최종 성과 평가 (딱 1회만 사용) |

### 과적합 방지

**Monte Carlo 시뮬레이션**:
거래 순서를 1000번 무작위로 셔플해서 equity curve를 다시 계산합니다.
운이 좋아서 성과가 잘 나온 건 아닌지 검증하는 것입니다.

- 95% 신뢰구간 하한 (즉, 최악의 5%)이 승인 기준을 충족해야 통과
- `sharpe_lower` (5th percentile), `mdd_upper` (95th percentile) 계산

**과적합 감지 지표**:

| 지표 | 경고 기준 | 의미 |
|------|----------|------|
| Train vs Test Sharpe 차이 | > 0.5 | 학습 데이터에만 맞춰진 것 아닌지 |
| 파라미터 민감도 | ±10% 변경 시 성과 50% 하락 | 특정 설정에만 의존하는 것 아닌지 |
| 시장 레짐별 성과 | 한 레짐에서만 수익 | 특정 시장 상황에서만 작동하는 것 아닌지 |

### 멀티 자산 백테스팅

| 자산군 | 데이터 소스 | 수수료 | 슬리피지 |
|--------|-----------|--------|---------|
| 미국 주식 | Yahoo/Polygon | 0.1% | ATR × 0.1 |
| 크립토 | Binance 히스토리 | 0.1% | ATR × 0.2 |
| 선물 | CME/MT5 | $2/계약 | 1 tick |

## 6. 페이퍼 트레이딩 — 실전 시뮬레이션

백테스팅을 통과한 전략을 실시간 시장에서 가상의 돈으로 테스트합니다.
실거래와 100% 동일한 로직을 사용하되, 실제 주문은 나가지 않습니다.

### 가상 포트폴리오 설정

| 항목 | 값 | 설명 |
|------|------|------|
| 초기 자본 | $10,000 | 실거래 전환 시에는 $500부터 시작 |
| 수수료 | 실제와 동일 | 브로커별 수수료 그대로 적용 |
| 슬리피지 | 실제 + 0.05% | 일부러 보수적으로 추정 (실제보다 불리하게) |
| 체결 방식 | 다음 캔들 시가 | 즉시 체결로 가정하지 않음 (현실적) |
| 리스크 규칙 | 실거래와 동일 | 서킷브레이커도 똑같이 작동 |

### 실시간 운영 흐름

```
실시간 시장 데이터 (Binance/Polygon WebSocket)
    │
    ├── decision-pipeline (LLM → RL → Rule) 동일하게 작동
    │   └── 시그널 생성 (실거래와 100% 동일한 로직)
    │
    ├── 가상 주문 실행
    │   ├── 슬리피지 시뮬레이션 (보수적)
    │   ├── 수수료 차감
    │   └── 다음 캔들 시가로 체결
    │
    └── 성과 기록
        ├── PostgreSQL: trading.paper_trades
        └── 일일 리포트 생성
```

### 실거래 전환 기준

30일 이상 운영한 뒤, 아래 조건을 모두 만족하면 실거래로 전환합니다.

## 시작하기

### 권장 순서

```
1. 백테스팅 (2주)
   └── 전략 선택 → Walk-Forward 검증 → Monte Carlo → 승인 기준 통과

2. 페이퍼 트레이딩 (30일)
   └── 가상 $10K → 실시간 운영 → 전환 기준 7개 항목 통과

3. 소액 실거래 (점진적 증액)
   └── $500 → $2K → $5K → $10K+
       각 단계에서 MDD > 15%이면 이전 단계로 롤백
```
